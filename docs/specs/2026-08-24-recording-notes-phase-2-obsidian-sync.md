# Recording Notes Obsidian Sync (Phase 2) Specification

Status: Draft v1

ADR: [docs/decisions/2026-08-24-recording-notes-obsidian-sync-direction.md](../decisions/2026-08-24-recording-notes-obsidian-sync-direction.md)

Purpose: Sync recording notes (generated by Phase 1) into the Obsidian vault, pull-only, following the same PersonalAccessToken + v1 REST API pattern already proven for Projects and Tasks.

This spec is a living document: when implementation deviates from it or new requirements surface, update it in the same PR as the change.

## 0. Background

Full Discovery Summary and the sync-direction decision live in the linked ADR. Summary: recording notes (Phase 1) had no path into Obsidian; only Project and Task notes synced, via `marvis-obsidian`'s existing pull/push commands. The ADR decided recording notes sync **one-way** (pull only, no push endpoint), reusing the existing `marvis_synced_hash` compare-and-skip guard rather than inventing conflict handling — because nothing in Discovery asked for editing recording notes from Obsidian, unlike Project notes which are human-authored either way.

## 1. Problem Statement

A recording's generated notes (`Recording.summary`) exist only inside the calendar app's own UI (`RecordingsList.tsx`). There is no way to browse, search, or link them alongside the rest of a course's material in Obsidian — where Project and Task notes already live.

**Important boundary:** this system syncs *notes* (`Recording.summary`), not the raw transcript (`Recording.transcript`) or action items (`Recording.actionItems`) — see Non-Goals.

## 2. Goals and Non-Goals

### Goals
- A new plugin command, "Pull recordings as notes," writes one vault note per `DONE` recording with a non-empty `summary`, mirroring the existing `pullProjects`/`pullTasks` pattern exactly (same collision guard, same hash-guard skip-on-local-edit).
- The v1 API's recording list endpoint is extended to include `summary` and `title`'s associated `projectId`/`title`-collision-safe id, so the plugin can pull without an extra per-recording request.
- No push counterpart — this is intentionally one-way, per the ADR.

### Non-Goals
- Pushing edits made in Obsidian back to `Recording.summary` — the ADR's explicit decision; not revisited here.
- Syncing `Recording.transcript` (the raw, often much longer, machine transcript) — permanent non-goal for this phase; nothing in Discovery asked for it, and it's a materially different, larger artifact than "notes." Can be requested as its own effort later.
- Syncing `Recording.actionItems` directly as vault content — action items already have a path into the vault: `createTasksFromRecordingAction()` turns a reviewed action item into a `Task`, and Tasks already sync via the existing `pullTasks`/`pushTasks` commands. No new plumbing needed.
- Recordings that are still processing, or `FAILED`, or `DONE` with an empty `summary` — silently excluded from the pull, not an error.

## 3. System Overview

### Main Components
1. `GET /api/v1/recordings` (modified, `src/app/api/v1/recordings/route.ts`) — list response gains a `summary` field per recording.
2. `pullRecordings()` (new, `marvis-obsidian/main.ts`) — fetches recordings, writes/updates vault notes under `Marvis/Recordings`, following the established pull pattern.
3. `buildRecordingFrontmatter()` (new, `main.ts`) — frontmatter builder for a recording note, mirroring `buildProjectFrontmatter`/`buildTaskFrontmatter`.

### Abstraction Levels/Layers
- **API layer**: `src/app/api/v1/recordings/route.ts` — one field added to an existing response; no new route.
- **Plugin layer**: `marvis-obsidian/main.ts` — all new code is here, following the file's existing single-class structure.

### External Dependencies
- `requireApiUser()` (`src/lib/apiAuth.ts`) — unchanged, already covers the recordings endpoints.
- Obsidian's `requestUrl`, `metadataCache`, `vault` APIs — same as every existing pull command.

## 4. Core Domain Model

No Prisma schema changes. No new plugin settings.

**Vault entity: recording note**
- Path: `Marvis/Recordings/<sanitized title>.md` (sanitized via the existing `sanitizeFilename()`).
- Frontmatter:
  - `marvis_recording_id` (string) — the recording's id; the collision/ownership check, identical role to `marvis_project_id`/`marvis_task_id`.
  - `marvis_project_id` (string, empty string if none) — lets a future feature (not this phase) group recording notes by course without a second API call.
  - `marvis_synced_hash` (string) — sha256 of the body, same hash-guard mechanism as Projects/Tasks.
  - `status` (string) — always `DONE` for a synced note (Section 2, Goals); present for consistency with the Task frontmatter's `status` field and so a stale note is visually identifiable if ever reused for a re-run recording.
  - `durationSec` (number, empty if null).
- Body: the recording's `summary` markdown, unmodified (already contains the Key points / Clarifications / Connections callouts from Phase 1's `renderNotes()`).

**Normalization Rules:** filenames follow the existing `sanitizeFilename()` (replaces `\/:*?"<>|` with `-`, trims, caps at 200 chars, `"untitled"` if empty) — unchanged. One addition specific to recordings (Section 5.2): a title collision with an unrelated, differently-owned note falls back to appending a short id suffix, rather than only skipping — see rationale there. A recording renamed in the app after its note was first synced gets a second, new-titled note on the next pull rather than the old note being renamed or removed — identical to how `pullProjects`/`pullTasks` already behave on a rename; not a new limitation introduced here.

## 5. Subsystem Specifications

### 5.1 `GET /api/v1/recordings` — add `summary`

**Intent:** Traces to the Goals — the plugin needs `summary` to write note bodies; without it in the list response, pulling N recordings costs N+1 requests (one list + one detail per recording), which the existing Project/Task pulls never need (their list endpoints already return `notes` inline).

In `src/app/api/v1/recordings/route.ts`'s `GET` handler, add `summary: r.summary` to the mapped object (alongside the existing `id`, `title`, `status`, etc.). No other field changes; the detail endpoint (`GET /api/v1/recordings/[id]`) is untouched.

### 5.2 `pullRecordings()`

**Intent:** Traces to the Goals and the ADR's Decision — this is the one-way sync itself, and it must reuse the proven hash-guard rather than invent new conflict handling (the ADR's explicit rationale).

```ts
const RECORDINGS_FOLDER = "Marvis/Recordings";

type MarvisRecording = {
  id: string;
  title: string;
  status: string;
  summary: string | null;
  projectId: string | null;
  durationSec: number | null;
};

async pullRecordings() {
  try {
    const { recordings } = await this.api<{ recordings: MarvisRecording[] }>("/api/v1/recordings");
    await this.ensureFolder(RECORDINGS_FOLDER);
    let created = 0, updated = 0, skipped = 0, excluded = 0;
    for (const recording of recordings) {
      if (recording.status !== "DONE" || !recording.summary) {
        excluded++;
        continue;
      }
      const path = this.recordingNotePath(recording);
      const existing = this.app.vault.getAbstractFileByPath(path);
      const body = recording.summary;
      // Hash the body WITH the trailing newline the file is about to be
      // written with (`${frontmatter}\n${body}\n`) — bodyWithoutFrontmatter()
      // strips only leading newlines after the frontmatter delimiter
      // (main.ts:126-132), so a re-read always yields `body + "\n"`, never
      // bare `body`. Hashing bare `body` here would make marvis_synced_hash
      // never match what the next pull recomputes from disk, so the guard
      // would treat every unedited note as "locally changed" and refuse to
      // update it, forever, after the very first write — recordings have
      // no push to ever resync that hash, unlike Projects/Tasks.
      const hash = sha256(`${body}\n`);

      if (!existing) {
        await this.app.vault.create(path, `${this.buildRecordingFrontmatter(recording, hash)}\n${body}\n`);
        created++;
        continue;
      }
      const cache = this.app.metadataCache.getCache(path);
      const fm = cache?.frontmatter;
      if (fm?.marvis_recording_id !== recording.id) {
        new Notice(`Marvis: skipped "${recording.title}" — a note with that filename already exists and isn't linked to this recording.`);
        skipped++;
        continue;
      }
      if (fm?.marvis_synced_hash && fm.marvis_synced_hash !== sha256(this.bodyWithoutFrontmatter(await this.app.vault.read(existing as TFile), path))) {
        new Notice(`Marvis: skipped "${recording.title}" — local changes to this note haven't been reconciled.`);
        skipped++;
        continue;
      }
      await this.app.vault.modify(existing as TFile, `${this.buildRecordingFrontmatter(recording, hash)}\n${body}\n`);
      updated++;
    }
    new Notice(`Marvis: pulled recordings — ${created} created, ${updated} updated, ${skipped} skipped, ${excluded} not yet ready.`);
  } catch (err) {
    new Notice(`Marvis: pull recordings failed — ${(err as Error).message}`);
  }
}
```

Note the skip-notice wording differs slightly from Projects/Tasks ("haven't been reconciled" vs. "haven't been pushed yet") — deliberate, since there is no push path to reconcile *through*; the user's only recourse is to manually copy their edit elsewhere and let the next pull overwrite, or rename the note to break the link. This is the Negative consequence the ADR already names.

### 5.2.1 `recordingNotePath()` — title-collision fallback

**Intent:** `createRecording()` (`recordings.ts`) defaults an untitled upload to `"Untitled recording"` (confirmed in the Phase 1 spec's review) — recording titles collide far more often in practice than Project or Task titles do, so reusing the plain "skip on any collision" behavior verbatim would make the common case (several untitled lecture recordings in the same course) silently fail to sync after the first one. This is new to recordings; Projects/Tasks are not changed.

```ts
private recordingNotePath(recording: { id: string; title: string }): string {
  const base = normalizePath(`${RECORDINGS_FOLDER}/${sanitizeFilename(recording.title)}.md`);
  const existing = this.app.vault.getAbstractFileByPath(base);
  if (!existing) return base;
  const fm = this.app.metadataCache.getCache(base)?.frontmatter;
  // No cached frontmatter yet (metadataCache not populated — e.g. right
  // after vault open, or a large-vault reindex in progress) means
  // ownership is genuinely unknown, not "owned by someone else." Treating
  // it as a collision here would fabricate a duplicate note for this
  // recording; returning the base path instead defers the real check to
  // pullRecordings()'s own existing frontmatter comparison, which already
  // fails safe (skip + Notice) exactly like pullProjects/pullTasks do
  // under the same staleness. Only a POSITIVE mismatch — cache present,
  // id different — is treated as an actual collision.
  if (!fm || fm.marvis_recording_id === recording.id) return base;
  return normalizePath(`${RECORDINGS_FOLDER}/${sanitizeFilename(recording.title)} (${recording.id.slice(0, 6)}).md`);
}
```

Synchronous, not `async` — no `await` in its body; the earlier draft's `async` was unnecessary (harmless either way since the one call site already awaits, but removed for clarity). This changes what "collision" means for recordings only: the suffixed path is checked next, and if *that* path exists and is linked to a different recording again (vanishingly unlikely — would require two ids sharing a 6-character prefix), the existing skip-with-Notice behavior in `pullRecordings()` still applies as the final fallback.

### 5.3 `buildRecordingFrontmatter()`

**Intent:** Traces to Section 4's domain model — this is the exact serialization of that model.

```ts
private buildRecordingFrontmatter(recording: MarvisRecording, hash: string): string {
  return [
    "---",
    `marvis_recording_id: ${recording.id}`,
    `marvis_project_id: ${recording.projectId ?? ""}`,
    `marvis_synced_hash: ${hash}`,
    `status: ${recording.status}`,
    `durationSec: ${recording.durationSec ?? ""}`,
    "---",
  ].join("\n");
}
```

### 5.4 Command registration

In `onload()`, alongside the four existing commands:
```ts
this.addCommand({
  id: "marvis-pull-recordings",
  name: "Pull recordings as notes",
  callback: () => this.pullRecordings(),
});
```
No push command is registered — per the ADR, there is none.

## 6. Failure Model

### Failure Classes
1. **API call failure** (existing pattern) — `this.api()` throws (network error, non-2xx, missing settings). Caught by `pullRecordings()`'s own `try/catch`, surfaced as a `Notice`, identical to every existing pull/push command. No new failure class.
2. **Per-recording collision or local-edit conflict** — not a failure; counted in `skipped` and surfaced once in the summary `Notice`, same as Projects/Tasks today.

### Recovery Behavior
- A recording that fails to sync (title collision even after the Section 5.2.1 fallback) is retried automatically on the next `pullRecordings()` run — no persistent "don't retry" state, matching the existing commands' statelessness.

### Restart Recovery
Not applicable — the plugin holds no in-progress state between command invocations; every run starts from the vault's and the server's current state.

## 7. Security

**Trust Boundary:** Unchanged — the same `PersonalAccessToken` + `requireApiUser()` boundary already governs every v1 API route, including the modified `GET /api/v1/recordings`. Adding `summary` to the response exposes no new data class (a user could already fetch any individual recording's `summary` via `GET /api/v1/recordings/[id]`, unchanged).

**Secret Handling:** Unchanged — no new secrets.

## 8. Test and Validation Matrix

**Core Conformance**
- `GET /api/v1/recordings` includes `summary` in each list entry (existing API test file, if any, otherwise a manual `curl` check — this repo has no test coverage for its API routes today, consistent with the rest of `src/app/api/v1/*`).
- `pullRecordings()` excludes a recording whose `status` isn't `DONE`.
- `pullRecordings()` excludes a `DONE` recording with a null/empty `summary`.
- `recordingNotePath()` returns the plain path when no note exists yet at that path.
- `recordingNotePath()` returns the plain path when the existing note at that path already belongs to this recording (re-pull of the same recording).
- `recordingNotePath()` returns the suffixed path when the existing note belongs to a different recording (or is unrelated).
- `recordingNotePath()` returns the **base** path (not the suffixed one) when the existing note's frontmatter cache is not yet populated (`fm` undefined) — fails safe to "assume mine, let the real check downstream decide" rather than fabricating a duplicate.
- `pullRecordings()` skips (does not overwrite) a note whose local content hash no longer matches `marvis_synced_hash`.
- The hash computed at write time (`sha256(`${body}\n`)`) equals the hash `bodyWithoutFrontmatter()` would recompute from a freshly-read, unedited file — i.e. an immediate re-pull with no local edits and an unchanged server-side summary reports 0 created/updated and the note is left alone (not flagged as "locally changed").

**Real Integration**
- Run `pullRecordings()` against a real Marvis instance with at least two `DONE` recordings sharing the default "Untitled recording" title — confirm both land in the vault as separate notes (this is exactly the case Section 5.2.1 exists for).
- Manually edit a synced recording note's body in Obsidian, then re-run the pull — confirm the edit survives (the note is skipped, not overwritten) and the skip is reported in the summary Notice.
